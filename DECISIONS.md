# Решения по проекту

## 2026-11-15 — PostgreSQL запускаем в Docker
- **Выбрали:** сервис `db` (образ `postgres:17`) в `docker-compose.yml`, данные хранятся в томе `pgdata`.
- **Альтернативы:** поставить PostgreSQL прямо на Windows; облачная БД.
- **Почему:** одна команда `docker compose up -d` поднимает одинаковую базу у всех и в CI. Windows не засоряется, путь с символом ` не мешает. Позже в этот же файл добавим Redis, Celery и бота.

## 2026-11-15 — Пароли и настройки храним в `.env`
- **Выбрали:** настройки лежат в `.env`, его нет в git (он в `.gitignore`). В git коммитим шаблон `.env.example`.
- **Альтернативы:** записать значения прямо в `docker-compose.yml` или в код.
- **Почему:** секреты не попадают в репозиторий, а на сервере можно подставить другие значения, не меняя код.

## 2026-11-15 — SQLAlchemy синхронный, драйвер psycopg 3
- **Выбрали:** синхронный SQLAlchemy 2.x (`def`, `Session`) и драйвер `psycopg`. Миграции делаем через Alembic.
- **Альтернативы:** асинхронный SQLAlchemy с `asyncpg`; создавать таблицы через `Base.metadata.create_all()` без миграций.
- **Почему:** синхронный код проще понять, отлаживать и тестировать. Celery тоже синхронный. Для MVP скорости хватает. Alembic хранит историю изменений схемы, и на сервере базу можно обновить без потери данных, а `create_all` только создаёт отсутствующие таблицы и не умеет менять существующие.

## 2026-11-15 — Защита от двойной записи: EXCLUDE-ограничение в PostgreSQL
- **Выбрали:** `EXCLUDE USING gist (barber_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'booked')`. Нужно расширение `btree_gist`.
- **Альтернативы:**
  1. Проверка в Python («SELECT пересечения, потом INSERT»). Есть гонка: два запроса одновременно делают SELECT, оба видят, что время свободно, и оба вставляют запись.
  2. `UNIQUE(barber_id, start_at)`. Ловит только одинаковое начало, а пересечение 12:00–13:00 и 12:30–13:30 пропускает.
  3. `SELECT ... FOR UPDATE` или advisory lock. Работает, но защита держится на том, что каждое место в коде не забудет взять блокировку.
- **Почему:** проверку делает сама база, атомарно, при любом способе вставки. `[)` означает «конец не входит», поэтому записи встык (12–13 и 13–14) разрешены. `WHERE status = 'booked'` нужен, чтобы отменённая запись освобождала время. В коде ловим `IntegrityError` с именем этого ограничения и возвращаем 409.

## 2026-11-15 — Время храним с часовым поясом
- **Выбрали:** `timestamptz` для записей, API принимает время только с указанием пояса (`AwareDatetime`). График мастера (`time`) считаем в поясе барбершопа (`TIMEZONE=Asia/Almaty`).
- **Альтернативы:** хранить время без пояса и считать его местным.
- **Почему:** без пояса легко ошибиться на несколько часов, когда сервер, Celery и Telegram работают в разных поясах.

## 2026-11-15 — Бот работает с базой напрямую через `app/booking.py`
- **Выбрали:** бот (aiogram 3, отдельный процесс `python -m bot`) вызывает те же функции бизнес-логики, что и API. Синхронные вызовы БД выполняются через `asyncio.to_thread`.
- **Альтернативы:** бот ходит в FastAPI по HTTP; отдельный асинхронный слой БД только для бота.
- **Почему:** правила записи (график, двойная запись, статусы) описаны в одном месте. Через HTTP понадобились бы своя авторизация бота и работающий API. `to_thread` не даёт синхронному запросу заблокировать бота.

## 2026-11-15 — Шаги записи в боте хранятся в callback_data, а не в FSM
- **Выбрали:** каждая кнопка несёт всё, что выбрано до неё (`svc → brb → day → slot → cfm`).
- **Альтернативы:** FSM aiogram (состояние в памяти или в Redis).
- **Почему:** не нужно хранилище состояний, бот можно перезапустить посреди записи, кнопка «Назад» делается просто. Окончательную проверку свободного времени всё равно делает база при создании записи.

## 2026-11-15 — Напоминания: периодическая задача, а не задача с eta
- **Выбрали:** Celery Beat раз в 5 минут запускает `send_reminders`. Задача находит записи, до которых осталось меньше 2 часов, и помечает их полем `reminder_sent_at`.
- **Альтернативы:** при создании записи ставить задачу с `eta = start_at - 2ч`.
- **Почему:** если запись отменили или перенесли, задачу с `eta` пришлось бы искать и отзывать. При брокере Redis задачи с `eta` больше часа могут выполниться дважды (из-за `visibility_timeout`), а при сбросе Redis пропадут. Периодическая задача каждый раз смотрит на текущее состояние базы.
- **Без повторов:** `UPDATE ... WHERE reminder_sent_at IS NULL RETURNING id` атомарен. Две задачи, запущенные одновременно, не возьмут одну и ту же запись.
- **Ошибки отправки:** временная ошибка (сеть, 5xx) снимает отметку, и через 5 минут будет новая попытка. Постоянная (400/403, например бот заблокирован) не повторяется.
- **Кому не напоминаем:** тому, кто записался меньше чем за 2 часа до визита.

## 2026-11-15 — В записи хранится цена на момент бронирования
- **Выбрали:** столбец `appointments.price`, в него копируется цена услуги при записи.
- **Альтернативы:** считать выручку по текущей `services.price`.
- **Почему:** если услугу подорожают, выручка за прошлые дни не изменится, а клиент заплатит ту цену, которую видел при записи.

## 2026-11-15 — Celery отправляет в Telegram через httpx, а не через aiogram
- **Выбрали:** синхронный `httpx.post` в Bot API (`app/telegram.py`).
- **Альтернативы:** `asyncio.run()` с aiogram `Bot` внутри задачи.
- **Почему:** задачи Celery синхронные, а нужен один HTTP-запрос. Запускать event loop в каждой задаче лишнее.

## 2026-11-15 — Вход в кабинет: JWT, пароли в Argon2
- **Выбрали:** таблица `users` с ролями `admin` и `barber`. Аккаунт мастера связан с `barbers` через уникальный `barber_id`, `CHECK` не даёт привязать админа к мастеру. Пароль хэшируется Argon2 (`pwdlib`). Вход через `POST /auth/token` (OAuth2 password flow) выдаёт JWT HS256 на 12 часов.
- **Альтернативы:** серверные сессии в Redis или БД; bcrypt.
- **Почему:** JWT не требует хранилища сессий, а кнопка Authorize в `/docs` работает сразу. В токене лежит только id пользователя, роль и активность каждый раз читаются из базы, поэтому отключённый аккаунт теряет доступ сразу. Минус: выданный токен нельзя отозвать до истечения срока, кроме как отключив аккаунт. Argon2 сейчас рекомендуемый алгоритм хэширования (OWASP).
- **Защита от перебора логинов:** если логина нет, пароль всё равно сверяется с фиктивным хэшем, чтобы по времени ответа нельзя было понять, существует ли логин.

## 2026-11-15 — Права проверяются в бизнес-логике, а не только в роутере
- **Выбрали:** админские эндпоинты закрыты зависимостью `require_admin`. Ограничения мастера (только свои записи, только «пришёл» / «не пришёл») проверяет `booking.change_status(..., barber_id=...)`.
- **Почему:** API и веб-страницы вызывают одну и ту же функцию, и правило нельзя забыть в одном из мест. Чужая запись возвращает 404, а не 403, чтобы не раскрывать, что такой id существует.
- **Новое правило:** «пришёл» и «не пришёл» можно отметить только после начала записи.

## 2026-11-15 — Веб-кабинет: Jinja2 на сервере, JWT в cookie
- **Выбрали:** HTML-страницы рендерит FastAPI (Jinja2), формы отправляются обычным POST. JWT хранится в cookie с `HttpOnly` и `SameSite=Lax`, а на сервере с HTTPS ещё и с `Secure` (`COOKIE_SECURE=true`).
- **Альтернативы:** SPA (React) с токеном в `localStorage`; отдельный CSRF-токен в каждой форме.
- **Почему:** не нужны фронтенд-сборка и отдельный проект. `HttpOnly` не даёт украсть токен через XSS, `SameSite=Lax` не даёт отправить POST-форму с чужого сайта (CSRF). Для MVP этого достаточно. API (`/appointments` и другие) принимает только `Authorization: Bearer`, поэтому cookie на API не действует.

## 2026-11-15 — Один Docker-образ для всех Python-сервисов
- **Выбрали:** один `Dockerfile`. Сервисы `api`, `bot`, `worker`, `beat` и `migrate` отличаются только `command` в `docker-compose.yml`, общие настройки вынесены в якорь `x-app`.
- **Альтернативы:** отдельный образ на каждый сервис.
- **Почему:** код и зависимости у всех общие. Один образ собирается один раз, и версии сервисов не могут разойтись.
- **Миграции** применяет отдельный сервис `migrate`, остальные ждут его через `service_completed_successfully`. Если запускать миграции при старте `api`, при нескольких копиях API они будут выполняться одновременно.

## 2026-11-15 — Зависимости: requirements.txt и requirements-dev.txt
- **Выбрали:** `requirements.txt` для приложения и образа, `requirements-dev.txt` (`-r requirements.txt` плюс pytest и ruff) для разработки и CI.
- **Почему:** в рабочем образе не нужны инструменты тестирования, так он меньше и в нём меньше лишнего кода.
- **На чём споткнулись:** `kombu` импортирует `packaging`, но не объявляет его в зависимостях. Ошибку поймал запуск worker в Docker, хотя локальные тесты проходили. Вывод: образ нужно запускать, а не только собирать, поэтому в CI есть проверка импорта внутри образа.

## 2026-11-15 — CI: линтер, проверка миграций, тесты, сборка образа
- **Выбрали:** GitHub Actions с тремя параллельными задачами. `lint` запускает `ruff check` и `ruff format --check`. `test` поднимает PostgreSQL 17 как service container, применяет миграции, выполняет `alembic check` (модели совпадают с миграциями) и pytest. `docker` собирает образ и проверяет, что в нём импортируется приложение.
- **Почему:** каждая задача ловит свой тип ошибок. `alembic check` ловит изменённую модель, для которой забыли написать миграцию.

## 2026-11-15 — Тесты на отдельной базе PostgreSQL
- **Выбрали:** база `barber_booking_test` в том же контейнере. Схему создаёт Alembic, после каждого теста таблицы очищаются через `TRUNCATE`.
- **Альтернативы:** SQLite в памяти; откат транзакции после каждого теста.
- **Почему:** SQLite не поддерживает `EXCLUDE` и `tstzrange`, а это главное, что нужно проверить. Откат транзакции не подходит для теста с одновременными запросами: каждому потоку нужна своя настоящая транзакция с commit.
